Steering Claude Code Without a Keyboard

Bryan Falkowski · October 19, 2026 · Builds on Robert Kovacs's post on coding hands-free with Claude Code and Wispr Flow

When we make delegating work to AI effortless, do we also make careful supervision less likely?

I ran into that question by building an interface for Claude Code from speech and an 8BitDo Micro game controller. Speech says what I want, and a thumb press approves what the agent did. It works, and a full session needed no keyboard. It also makes approving a change cost almost nothing, while reading the change costs what it always did.

This post covers what I built, what the HCI course I took says is good and bad about it, and how to test whether easy approval makes reviewers careless. It separates what I saw from what I only suspect.

Two inputs

Don Norman wrote The Design of Everyday Things about doors, stoves and light switches. He could not have pictured Claude Code. His principles still apply to it, because they are about people, and people have not changed.

Not long ago, writing code without opening an editor was new. With agents like Claude Code, you describe the change and approve what the agent does. "Writing code" is a loose term for that, since Claude writes it and I steer. If steering is the work, the input devices can be designed around it, and the keyboard is one choice among several. My guess, and it is only a guess, is that keyboards will one day look as dated as typewriters.

In a post from April 13, 2026, Robert Kovacs described steering Claude Code this way daily for several weeks, with the same controller and Wispr Flow for dictation. He found that talking makes him state the intent, constraints and edge cases up front, so Claude's first attempt lands closer. He also found that speech cannot approve anything. Saying "yes" types the word "yes" into the chat box, so approvals need a real key.

His first finding is about skill more than speed. Stating the intent, the constraints and the edge cases is the part of working with an agent that the agent cannot do for you. My guess is that speaking trains it, because a vague request sounds vague when you say it out loud, and a typed one is easy to send anyway.

That is the lens for the rest of this post. An interface for working with AI changes how fast you go, and it also changes what you practise. Speech may train you to say what you mean. One-press approval may train you to stop reading.

So the goal is not to take all the effort out of working with AI. It is to remove the effort that gets in the way of good work and keep the effort that builds skill. If speaking makes me clearer about what I want, that effort is worth encouraging. If one-press approval makes me less likely to examine a change, the effort it removed was the useful kind. Both are usability questions, but only one is about whether I can operate the interface. The other is about what the interface helps me get better at.

The prototype

The prototype has three parts, all on a Mac:

  • An 8BitDo Micro, a Bluetooth controller about the size of a keychain, sold for page turning and Anki. In keyboard mode the Mac sees it as a keyboard.
  • FluidVoice, a free, open-source dictation app. You hold a key, talk, and release, and it types the text wherever the cursor is. It runs speech models on the Mac unless you turn on a cloud provider.
  • Karabiner-Elements, a free, open-source key remapper. It can apply a rule to one device only, so the controller changes and the real keyboard does not.

Each button does one thing in Claude Code:

Three rounds to get it working

Round one: every button typed a letter. In keyboard mode, A types g, B types j, and the D-pad types c to f. Claude Code listens for Enter, Esc and the arrow keys, so out of the box the controller did nothing useful. 8BitDo's remapping app has no macOS version, and the iPhone version had a one-star rating when I looked, so I wrote a Karabiner rule instead.

Round two: the remap failed without saying so. After I approved Karabiner's permission prompts, the buttons still typed letters. Karabiner's log said the permissions were not granted, because its setup had stopped at the Accessibility step. Later, quitting Karabiner to restart it turned the remap off, and the buttons went back to letters with no warning. Both times the screen looked exactly like a rule with a typo. Only the log said what was wrong.

Round three: slash commands. Claude Code runs a command only when the message starts with a typed /. When I said "slash", FluidVoice typed the word. The fix was to map X to /. Pressing X opens Claude Code's command menu. Then I hold L and say one word from the command's name, such as "setup", and the menu shows only the commands that match. The D-pad moves to the right one, and A runs it. Dictation only has to get one ordinary word right, and picking from a short list is what the controller does well.

Using it

After round two, I used speech and the controller for the rest of the session. I installed a Claude Code plugin, pstack, and ran its setup, which asked four multiple-choice questions. I kept a count of every time I had to reach for the keyboard, because that count is the honest test of whether the interface works.

Reading it as an HCI problem

I took Foundations of Human Computer Interaction at RIT during my master's degree. It was an elective, and one of the more interesting subjects in the program. The course splits human error into two kinds. A mistake is choosing the wrong goal. A slip is having the right goal and doing the wrong thing, and the fix for a slip is better interface design. Almost everything that went wrong here is a slip, and the course has a name for each one.

These principles answer one question, whether people can use an interface. The next section asks a different one, what the interface trains people to do. Usability tells you whether you can approve with one press. It does not tell you whether you read first.

  • No signifiers. A signifier is Don Norman's term for a visible cue that tells you what an action will do. The buttons say A, B, X and Y, not Accept and Reject, so the mapping lives in your memory or on a table beside you. A label on screen that names each button's current action would fix this, and Claude Code's status line could show one.
  • No feedback. In round two, a broken remap and a working one with a typo looked the same. The Principles of Universal Design ask for "effective prompting and feedback during and after task completion". The setup gave none. Only a log file did.
  • A mode error waiting to happen. R switches Claude Code's permission mode, and in auto-accept mode Claude edits files without asking. The controller shows nothing about which mode you are in. The course defines a mode error as the same action meaning different things in different system states, and notes it is "more common with poor visibility of system state".
  • One thing it gets right. Holding L to talk is what the course calls a spring-loaded mode. FluidVoice listens only while the button is held, so you cannot leave the microphone on by forgetting which mode you are in.
  • Low physical effort. Universal Design's sixth principle asks for a neutral body position and fewer repetitive actions. Leaning back with a controller in one hand meets both better than a keyboard does, which is the strain Kovacs was trying to reduce.

The next version

The prototype is usable, not polished. Its value so far is that it works well enough to expose real design problems. Two choices held up and are worth keeping. Hold-to-talk keeps the microphone under the thumb's control. Speech for intent and a short menu for decisions give each input the part it handles well, which is why the slash command fix works. The next version would add three things:

  • Button labels on screen. A strip in Claude Code's status line naming what A, B, X and the D-pad do right now, so the controller has the signifiers it lacks.
  • A visible permission mode. The current mode shown wherever approvals happen, so pressing R can never leave you in auto-accept without knowing it.
  • A check that the remap is live. A small signal that Karabiner has taken over the controller, so a missing permission or a quit app shows up on screen instead of in a log.

Easier is not the same as better

With this interface, approving a change costs one press of the thumb. Reading what you approve costs the same as it did before. I expect that gap to pull toward approving without reading. Kovacs's post does not look at it.

The course has names for this risk too. A capture error happens when a frequent action takes over a rarer one that starts the same way. If A approves fifty routine prompts in a row, the press on the fifty-first prompt, the one that needed reading, is the same thumb movement. Reviewing AI output is also a vigilance task, meaning continuous attention to a long, monotonous stream where the rare problem is easy to miss. Universal Design principle 5d says what to do about it: "Discourage unconscious action in tasks that require vigilance."

Speed is the wrong measure for a review step, and the cost of careless review reaches past one change. Teams check AI systems against human judgments. My primer on LLM judges measures a judge against human labels, and its numbers are only as good as those labels. A reviewer who approves without reading makes the judge look better than it is, and every decision based on that number inherits the error. The interface a reviewer uses is part of the measurement, so how it shapes their attention is a measurement question as well as a design one.

If approving is cheap, the interface has to protect the reading that should come before it. These changes would help, and none of them slows down routine work:

  • Decide before you see the AI's answer. When you review a verdict or a summary, form your own view first, then compare. Once the AI's answer is on screen, agreeing with it takes the least effort.
  • Make a reason cheap to give. With voice, a spoken reason costs a few seconds. Asking for one on every rejection, and on a sample of approvals, makes you read the thing you are judging.
  • Make risky approvals cost more. Norman calls this a forcing function, a step that stops you from doing something by accident. Karabiner can make A act only when held for a second, another spring-loaded action. It cannot tell a risky prompt from a routine one, so the tool asking for approval would have to say which is which.
  • Tell reviewers when they missed one. The course's remedies for vigilance include knowledge of results when an event is missed. Mixing in items with known answers, and saying when one was approved by mistake, gives the reviewer that feedback while they work.

Whether the controller makes reviewers worse can be tested instead of guessed. A fair test needs more care than counting mistakes.

  • Use review items with known answers, some routine and some risky, with the risky ones rare, as they are in real work.
  • Score both directions. Count the problems the reviewer caught and the good items the reviewer wrongly rejected. A reviewer who rejects everything catches every problem, so accuracy alone would reward them. My primer uses the same two rates, TPR and TNR, to check an LLM judge.
  • Check the reasons. A rejection that names the real problem shows the reviewer read the item. One that names something else was a lucky guess.
  • Record the time per decision, as a cost to weigh, not as the goal.
  • Account for learning. Alternate batches between the keyboard and the controller, and discard the first batches with each, so learning the controller does not count against it.

Even then, a short study measures performance, not capability. It could tell me whether the controller changes how well people review in one session. It would not tell me whether the controller helps or hurts them as reviewers over time. That would take measuring whether people improve with practice, keep what they learn, and carry it over to unfamiliar kinds of change.

Time will tell

I do not know yet whether I will keep using this. Habits are strong, and some things, like an exact file path, may still be easier to type. What the experiment shows is narrower than a prediction about keyboards. For one workflow, steering Claude Code, from prompts to approvals to commands, the keyboard turned out to be optional. Whether that is good for the person steering is the question this post leaves open.

None of this is new for everyone. People who cannot use a keyboard have had other ways in for a long time, such as voice control and switch access, both built into macOS. What has changed is the work. When what we do at the computer becomes describing and deciding, the rest of us can step back from the keyboard too, and the old HCI principles tell us what to watch for when we do.

The controller is a small experiment, but the question applies to any AI tool that separates doing the work from approving it. Such tools should be judged on more than whether people can finish the task. They should also be judged on whether they help people make better decisions about the result.

Appendix: set it up yourself

You need the three pieces above and Claude Code in a terminal. I bought the Micro on Amazon.

Connect the controller.

  1. Slide the Micro's mode switch to K.
  2. Hold the pair button on the top edge for about 3 seconds, until the light blinks fast.
  3. On the Mac, open System Settings, then Bluetooth, and connect to "8BitDo Micro gamepad".
  4. Open TextEdit and press each button in a known order to see what it types.

Mine typed these:

ButtonSends
A, B, X, Yg, j, h, i
D-pad up, down, left, rightc, d, e, f
L, Rl, r
Plus, minuso, n
The two remaining buttonsk, m

Install Karabiner. The installer adds a keyboard driver, so it asks for your password.

brew install --cask karabiner-elements

Open Karabiner-Elements and follow its prompts. In System Settings, under Privacy & Security, turn on Karabiner-Core-Service in both Input Monitoring and Accessibility. Karabiner sees every key you type once you grant these, which is how any remapper works. Read its source if that matters to you. If the buttons still type letters, check /var/log/karabiner/core_service.log. It says when Karabiner has taken over the controller.

Add the rule. It goes in ~/.config/karabiner/karabiner.json, under profiles[0].complex_modifications.rules. Each line turns one letter into one key. The device_if condition limits the rule to the Micro by its vendor and product IDs, so your real keyboard still types g. Run system_profiler SPBluetoothDataType to confirm the IDs for your unit. Mine reported vendor 0x2DC8 (11720) and product 0x9021 (36897).

{
  "description": "8BitDo Micro: A=Enter, B=Esc, D-pad=arrows, L=FluidVoice, R=Shift+Tab, X=/",
  "manipulators": [
    { "from": "g", "to": "return_or_enter" },
    { "from": "j", "to": "escape" },
    { "from": "c", "to": "up_arrow" },
    { "from": "d", "to": "down_arrow" },
    { "from": "e", "to": "left_arrow" },
    { "from": "f", "to": "right_arrow" },
    { "from": "l", "to": "right_option" },
    { "from": "r", "to": "tab", "modifiers": ["left_shift"] },
    { "from": "h", "to": "slash" }
  ]
}

That is shorthand. Karabiner wants each line written out in full, with the device condition on every one. Here is the first line in Karabiner's format. The others follow the same shape.

{
  "type": "basic",
  "from": { "key_code": "g", "modifiers": { "optional": ["any"] } },
  "to": [{ "key_code": "return_or_enter" }],
  "conditions": [{
    "type": "device_if",
    "identifiers": [{ "vendor_id": 11720, "product_id": 36897 }]
  }]
}

Karabiner reloads the file when it changes. Press A in TextEdit to check. It should start a new line instead of typing g.

Notes. FluidVoice's hotkey was already right Option, so the L button only sends that key. Kovacs used a key combination for Wispr Flow because Wispr's default key, fn, could not be assigned to a controller button in 8BitDo's app. I left Y, plus, minus and the other two buttons alone. They still type letters, so a stray press puts a letter in your prompt. Map them to vk_none in the same rule if that happens to you.
