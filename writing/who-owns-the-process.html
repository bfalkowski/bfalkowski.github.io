Who Owns the Process? Spec Frameworks, Skills, and the Trust Ladder for Coding Agents

Bryan Falkowski · October 23, 2026 · Updated October 24, 2026

A growing set of tools tries to answer the same question: how should a coding agent know what to build, and how much of the work should it be trusted to do?

Spec-driven frameworks such as GitHub Spec Kit give agents an explicit plan to work from. Skill collections such as Matt Pocock's let developers teach agents specific ways of working. Other approaches combine these ideas, adding orchestration to coordinate agents and their work.

The interesting question is not which tool has the best workflow. It is how we get from an agent that needs constant supervision to one that can take on meaningful work with less intervention.

Specifications establish intent. Skills capture process. Verification closes the loop. That loop is what allows you to trust agents with more work.

Where I first saw it

In early June 2025, I spent two days at AWS headquarters in Crystal City, Virginia, working with Amazon Q IDE and an early prototype of AI-DLC, the AI-Driven Development Life Cycle.

The workflow was straightforward in principle. We iterated on acceptance criteria, used those to generate a specification, refined the spec, and then used it to drive implementation. The specification was not just documentation written after the fact. It was an artifact that the agent could help create and then use as the basis for building.

On the Amtrak home, I tried applying the idea to a real project. Somewhere on that ride I realized I was facing two separate problems. The first was figuring out how to coordinate the work. The second was knowing whether the work was any good.

The first problem gets a lot of attention. How many agents should run? Which tools should they have? How should tasks be divided? Which model should handle each role?

The second problem is harder to ignore once you have tried to automate more than a small coding task. How do you know the agent actually did what you asked? How do you distinguish a convincing explanation from a correct result? And how much evidence do you need before you let it do more on its own?

That last question is where I have become most interested in evaluation.

Specifications and skills solve different problems

A specification makes intent explicit. It gives the agent a description of the desired behaviour, constraints, and acceptance criteria instead of leaving it to infer everything from a conversation.

A skill captures a repeatable way of working. It might guide an agent through test-driven development, help it investigate a bug, or force it to work through the unresolved questions in a plan before writing code.

These are complementary. A good specification does not tell you everything about how to implement a change. A good skill does not necessarily tell you what the change should accomplish.

The distinction becomes clearer when comparing GitHub Spec Kit with Matt Pocock's skills.

Spec Kit: the process owns the work

Spec Kit provides a structured approach to spec-driven development. Its workflow can establish project-wide rules, define what a feature should do, produce a technical plan, break that plan into tasks, and implement them.

The important idea is that the documents are connected. The implementation is supposed to follow the specification and plan, rather than allowing the code to become the only record of what was intended.

That creates useful discipline. A team can review a proposed change before implementation, agree on the requirements, and hand work to another developer or agent without relying on the original conversation. Project-wide rules can be written down once and applied across features.

The cost is process. If a task is exploratory or the requirements are still changing, formalizing every step can feel like overhead. The documents also need to stay current. A specification that no longer describes the code can become another source of confusion.

Spec Kit has evolved toward more flexible entry points, so it is no longer accurate to treat every use as a rigid sequence of mandatory phases. Still, its strength is the ability to make the plan a durable artifact.

Matt Pocock's skills: you own the process

Pocock's skills take a more modular approach. Instead of starting with a prescribed pipeline, you can choose the behaviour you need for the task in front of you.

A grilling skill helps resolve the unanswered questions in a plan. Domain modeling builds a shared glossary and records architectural decisions. A TDD skill guides implementation through red, green, and refactor. Other skills help with debugging, prototyping, and code review.

This works well when the right process depends on what you are trying to learn. If an idea is vague, start by exploring it. If the design is uncertain, prototype it. If the change is obvious, there may be no reason to run through a lengthy planning workflow.

The trade-off is that the developer must decide which process to use and make sure important decisions are recorded somewhere durable. Flexibility is useful, but it can also lead to inconsistency.

The difference is not that one approach has process and the other does not. Both do. The difference is how much of the process is prescribed and who decides what happens next.

The missing piece is verification

Neither a specification nor a skill guarantees a correct result.

A specification can be clear and still be implemented incorrectly. A skill can describe a sound process and still produce a faulty change. An agent can follow every step and arrive at the wrong answer.

That is why verification matters so much.

Lauren Tan, known as poteto, makes this point in her conversation with Matt Pocock about coding agents and scaling software development. She describes the problem of relying on herself as the intermediary between an agent and its output:

"I was still relying on me as the proxy between my agent and the output."

That is a useful description of the limit I had hit. The agent could generate code quickly, but I still had to inspect the result, decide whether it was right, and determine what should happen next. The coding work was automated, but the evaluation work was still mine.

Tan puts verification at the centre of improving that arrangement:

"The single most important skill that should be in your toolkit is verification."

The point is not simply to add more tests or ask another model whether the first model did a good job. It is to give the agent a reliable way to gather evidence about its own output.

Depending on the task, that evidence might come from running tests, checking types, comparing a result against acceptance criteria, inspecting a rendered interface, or evaluating an output against a defined rubric. Different tasks require different checks. A passing test suite is meaningful evidence, but it does not prove that every requirement has been met.

Verification also needs to happen early enough to influence the work. Tan makes the connection explicit:

"If the agent can't actually see the result of its work there's no way it can actually iterate."

An agent that cannot observe the consequences of its actions has to rely on assumptions. An agent that can inspect the result, compare it with the intended outcome, and use the feedback to make corrections has a path toward improving its work without requiring a human to mediate every step.

That changes the role of orchestration. Coordinating more agents may increase throughput, but it does not automatically increase confidence. If the system cannot tell good results from bad ones, it can simply produce more output that someone has to review.

Lauren Tan's trust ladder

Tan's trust-ladder framing offers a useful way to think about what comes next. As confidence in an agent's work increases, you can give it more responsibility and scale the work it performs. Trust is not an initial setting that you choose once. It develops as the system demonstrates that it can produce reliable results.

This matters because there is a difference between an agent that can perform a task and an agent that can perform it reliably enough to be given the task with less supervision.

A successful demonstration is not enough. Nor is a single good result. You need to understand how often the approach works, where it fails, and whether the checks you rely on actually catch those failures.

This is where evaluation becomes part of the development process rather than an afterthought.

My own work on LLM-as-a-judge reliability grew out of that concern. If a model evaluates another model's output, how stable is the score? Would the same response receive a different rating on another run? Does the evaluation agree with itself often enough to support a decision? Are the results useful for distinguishing better outputs from worse ones?

Those questions matter because an evaluation can look authoritative without being reliable. A score is not evidence of quality simply because it is numerical. Before using a judge to decide whether an agent has done good work, we need to understand the judge's own behaviour.

This is my application of Tan's trust-ladder idea to evaluation: trust should grow with the evidence we have, not simply with how impressive the latest model looks.

The practical goal is not to eliminate human judgment. It is to make human attention more valuable. People should spend their time on ambiguous requirements, difficult trade-offs, novel situations, and failures that need investigation, rather than repeatedly checking work that can be verified automatically.

Where the tools fit

The broader field is moving toward combinations of these ideas.

Kiro and Spec Kit put specifications at the centre of the workflow. AWS AI-DLC explores a process in which AI proposes and executes stages while people validate decisions. OpenSpec, BMAD, and GSD offer other ways to structure specification and implementation. Superpowers is a useful counterexample to the assumption that a skill pack always means a completely optional workflow: although it is packaged as skills, it can enforce a defined process.

Pocock's skills provide reusable techniques that can be applied where they are useful. Tan's pstack approaches the problem from another direction, focusing on how agents carry out work, how roles are assigned, and how results can be reviewed or compared.

These tools are not all trying to solve exactly the same problem. Some help define the work. Some guide how the work is done. Some coordinate execution. And verification determines whether the output is good enough to trust.

The categories overlap, but the distinctions are still useful. A specification can define acceptance criteria. A skill can guide the agent through a repeatable process. Orchestration can coordinate multiple attempts or roles. Evaluation can provide evidence about the result.

No one layer replaces the others.

A practical way to combine them

For an exploratory project, I would start with skills. The requirements are likely to change as I learn, and I want to keep the process lightweight. I can use a grilling session to sharpen the idea, prototype a design question, and introduce TDD once the behaviour is clear enough to preserve.

For a shared feature with explicit requirements and handoffs, I would lean toward a specification framework. A durable plan is valuable when multiple people or agents need to agree on what is being built and how success will be judged.

For a behaviour-preserving refactor, the central challenge is different. The goal is to change the internal structure without changing what the system does. A formal feature spec may help with scope, but the most important evidence comes from tests and other checks that demonstrate the existing behaviour has been preserved.

In all three cases, I would want verification to be part of the workflow from the beginning. It should not be a final step that produces a green checkmark after all the important decisions have already been made.

And when combining tools, I would keep one authoritative home for the plan. A specification, glossary, or architecture decision record can be refined by different skills, but the agent should not have to choose between conflicting versions of the truth.

The goal is justified trust

The debate over frameworks versus skills is useful, but it is not the end of the problem. We can debate how much process to prescribe, how many agents to coordinate, and which model should perform each task. Those decisions matter.

But the larger opportunity comes when the system can verify its own work and use the results to improve it.

Specifications establish intent. Skills capture process. Orchestration coordinates execution. Verification closes the loop.

Lauren Tan's trust ladder provides a useful framing for what that makes possible: giving agents more responsibility as confidence in their work grows. My interest in evaluation is in making that confidence measurable rather than assumed.

The goal is not to trust an agent because it can write code, follow a workflow, or produce a persuasive explanation. It is to trust it because we have evidence that the work meets the requirements, that the checks are meaningful, and that failures are likely to be caught.

That is what turns faster code generation into a development process that can reliably take on more work.
