Who Owns the Process? Spec Frameworks and Skill Packs for Coding Agents

Bryan Falkowski · October 23, 2026

There are a lot of tools now trying to solve the same problem: how do you get a coding agent to build the right thing, and how do you make sure it understands the decisions that matter?

Some tools, including GitHub Spec Kit, Kiro, OpenSpec, BMAD and GSD, give you a structured process built around specifications. Others, like Matt Pocock's skills, offer smaller pieces that you can bring into a workflow as needed.

At first glance, this looks like a choice between frameworks and skill packs. But the distinction isn't quite that simple. Superpowers, for example, is packaged as a collection of skills but expects the agent to follow a defined workflow.

The more useful question is who decides what happens next. Does the tool prescribe the process, or does the developer choose which steps are worth taking? And when the work is done, what is the authoritative record of the decisions?

I've spent time with Spec Kit and Pocock's skills, and they represent two useful starting points for thinking about these questions. The other tools fall somewhere between them. Here's how I see the differences, where each approach makes sense, and what I've learned about using them together.

Where I first saw it

In early June 2025, I spent two days at AWS headquarters in Crystal City, Virginia, working with Amazon Q and an early prototype of AI-DLC, the AI-Driven Development Life Cycle. The workflow was fairly straightforward: work with the AI to refine acceptance criteria, use those to produce a specification, iterate on the spec, and then use it to drive implementation. The IDE had tabs for the different documents, making each stage visible.

It was the first time I'd seen this approach up close, and I was interested enough to try it on the train ride home. I picked a real change in one of my projects: a refactor that would add an early version of an agent with tools.

It went badly. The process felt cumbersome, and the results weren't worth the effort. I came away thinking that the idea had promise, but the tooling wasn't there yet. I put it aside for a while.

The public releases followed over the next several months. Kiro entered preview in mid-July 2025, AWS published its AI-DLC approach on July 31, and GitHub's Spec Kit followed later that summer. In November, AWS open-sourced its AI-DLC workflows for coding agents.

Looking back, the prototype I saw at AWS feels primitive compared with what agents can do with specifications today. But the basic idea was already there: make the requirements explicit, work through the decisions before implementation, and give the agent a plan it can follow. What's changed is how much of that work the agent can handle and how practical the whole process has become.

The problem they're trying to solve

When an agent can write a lot of code, writing the code stops being the only challenge. The agent still needs to know what you're trying to accomplish, which constraints matter, and what decisions have already been made.

If that information lives only in a conversation, it can disappear when the context changes. Start a new session, switch models, or bring in another agent, and you may find yourself explaining the same things again. Leave too much unspecified, and the agent will fill in the gaps itself.

All of these tools try to address that problem. They give the agent some combination of requirements, plans, project rules, shared terminology and implementation guidance. Where they differ is how those pieces fit together.

There are two questions I find particularly useful.

First, who decides the next step? Some tools guide you through a sequence of stages. Others let you choose what you need for the task at hand.

Second, where do the decisions live? Is there a specification that the implementation is expected to follow, or is the lasting record spread across the code, project instructions and architecture decisions?

Spec Kit and Pocock's skills offer a useful contrast on both questions.

Spec Kit: start with the specification

GitHub's Spec Kit is built around spec-driven development. The idea is to make the specification an important part of the development process, rather than treating it as documentation that gets written and then forgotten.

Its familiar workflow uses a set of slash commands:

  • /speckit-constitution establishes the project's standing rules in .specify/memory/constitution.md.
  • /speckit-specify describes what to build and why, without getting into the technology choices.
  • /speckit-plan works out how to build it, including the technical approach, data model and contracts.
  • /speckit-tasks breaks the plan into individual tasks.
  • /speckit-implement carries out the implementation.

Each stage produces material that the next stage can use. Instead of asking an agent to go straight from an idea to code, you work through the decisions in a more deliberate way.

The philosophy behind the project is captured in a line from its design documentation:

Specifications don't serve code—code serves specifications.

That doesn't mean every line of code is mechanically generated from a document. It means the specification is supposed to remain authoritative. If the requirements change, update the spec and then bring the implementation into line with it.

The constitution is another important part of the approach. It records rules that should apply across the project, rather than leaving the agent to rediscover them for every feature. Examples include library-first design and test-first development. The plan template checks the constitution at multiple points, helping ensure that those rules are considered throughout the process.

This structure is useful when you need consistency. A team can agree on a common way to describe requirements, work through technical decisions and hand implementation tasks to people or agents. The resulting documents give everyone something concrete to work from.

The downside is the overhead. Not every change needs a full specification, and a process that works well for a substantial feature can feel excessive for a small fix. There's also the question of maintenance: if the code changes but the specification doesn't, the document that was supposed to provide clarity becomes another source of confusion.

Pocock's skills: choose the steps you need

Matt Pocock's skills take a different approach. Rather than starting with a prescribed sequence, they provide individual capabilities that you can use when they make sense.

A few examples I've found useful:

  • Grilling: Work through a plan by answering questions until the important decisions and edge cases are clear.
  • Domain modeling: Establish a shared vocabulary in GLOSSARY.md and record architectural decisions as ADRs.
  • TDD: Work in small red-green-refactor cycles, writing a failing test before implementing the behaviour.
  • Bug diagnosis, prototyping and code review: Investigate a problem, try out a design with throwaway code, or review a change before merging it.

The important difference is that you don't have to use them in a fixed order. If the problem is poorly defined, start by working through the requirements. If you're unsure about a design, prototype it. If the change is obvious, you might go straight to a test and implementation.

Pocock's README is explicit about the trade-off. It argues that approaches such as GSD, BMAD and Spec Kit can take control away from the developer by owning the process, making problems with that process harder to work around.

The skills are intended to be small enough to understand, change and combine. Rather than requiring every task to pass through the same stages, they let the developer decide how much process the work needs.

That flexibility comes with a cost. The developer has to know when to use each skill, and different people may approach the same problem differently. There is no guarantee that everyone will follow the same steps or produce the same intermediate artifacts.

The lasting record also looks different. The code, project instructions, glossary and architecture decision records carry much of the context. There isn't necessarily one feature specification that the implementation must follow.

I don't think either approach is inherently better. Spec Kit gives you a more consistent process, which can be valuable when several people or agents need to work from the same decisions. Pocock's skills give you more control, which is useful when the work is changing as you go.

The trade-off is between consistency and flexibility. How much of either you need depends on the work.

The other tools fall somewhere in between

Spec Kit and Pocock's skills are useful reference points, but they aren't the whole landscape. Most of the other tools lean toward providing a process, although they differ in how rigid that process is.

Superpowers is worth calling out because it exposes the weakness in the usual framework-versus-skills distinction. It is packaged as a set of skills, much like Pocock's collection, but its README describes them as mandatory workflows, not suggestions.

In other words, how a tool is packaged doesn't tell you how much control you have over the process. A collection of skills can enforce a workflow, and a framework can offer increasingly independent entry points.

AI-DLC adds another variation. In its current open-source form, the agent chooses which stages make sense for the task and proposes a plan for people to approve. AWS describes the division of responsibility this way: "Humans decide and validate, AI plans and executes."

That puts the process somewhere between a fixed sequence and a developer assembling each step. The agent proposes the workflow, but people retain control over whether to proceed.

I've worked directly with Spec Kit and Pocock's skills, so those are the two I can compare from experience. For the other tools, I'm describing their documented approaches rather than claiming equivalent hands-on experience.

The gap is getting smaller

The distinction between these approaches has become less clear over time.

Spec Kit's documentation now describes its commands as independent entry points rather than mandatory phases. It encourages starting with the smallest change that meets your needs and includes separate paths for things like fixing a bug or exploring an idea.

Pocock's collection has expanded in the other direction. It now includes skills such as to-spec, which turns a conversation into a specification; to-tickets, which breaks a spec into tickets; and implement-spec, which implements a specification using subagents.

That is much of a spec-driven workflow, but broken into pieces you can choose to use.

The difference, then, is increasingly about the default. Spec Kit gives you a structured process that you can pare back. Pocock's skills give you individual capabilities that you can assemble into a more structured process.

For me, that's a more useful way to think about the choice than deciding whether a tool belongs in the framework or skill-pack category.

Where pstack fits

I also use pstack, a port of Lauren Tan's (poteto's) skill stack. I haven't included it in the main comparison because it addresses a different part of the problem.

Spec Kit and Pocock's skills help you decide what to build and how to reason about the work. Pstack focuses more on how agents carry out that work: which models take which roles, when to run multiple attempts and compare their results, and how review fits into the process.

Those concerns are complementary. You could use a spec-driven workflow to define the work and pstack to organize the agents that implement it. Or you could use Pocock's skills to guide the development process and pstack to handle agent orchestration.

The tools operate at different levels, so there's no reason to treat them as competing alternatives.

Which approach would I use?

I find it helpful to think about three kinds of work. The right amount of structure isn't necessarily determined by the size of the project. It's determined by how much is already known and how much coordination the work requires.

An exploratory project: Pocock's skills

Consider a learning dashboard I'm building for myself. I'm the only user, the requirements aren't fully clear, and I expect to discover what I want as I build it.

Writing a detailed specification at the beginning would mean documenting a lot of assumptions that might not survive the first working prototype. I'd rather use grilling to clarify the idea, prototype the parts I'm uncertain about, and introduce TDD as the behaviour becomes clear enough to keep.

That doesn't mean skipping planning altogether. It means spending time on decisions when there's enough information to make them useful.

A behaviour-preserving refactor: probably Pocock's skills

I initially thought a large refactor, particularly one that changes the boundaries between modules, was an ideal candidate for Spec Kit. The amount of planning seemed to justify a formal process.

I'm less convinced now.

A refactor is supposed to change the internal structure without changing what the system does. A feature specification doesn't necessarily help much with that. The harder questions are where the module boundaries should be, which responsibilities belong together, and how to prove that existing behaviour still works after the changes.

Pocock's skills seem better suited to those questions. Domain modeling can help clarify responsibilities and terminology, while TDD and code review can help keep the changes under control.

A formal plan could still be useful for a particularly large refactor, especially when several people are involved. But I'd start with the specific problems to solve rather than assume that a full spec-driven process is the answer.

A feature shared across a team: Spec Kit

Spec Kit makes more sense when a feature needs to be understood and implemented by several people or agents, possibly across multiple sessions.

In that situation, the plan needs to survive the conversation that created it. The requirements must be clear enough for someone else to pick up the work, and the decisions need to remain consistent as implementation progresses.

A specification gives everyone a shared reference. The constitution establishes the rules that apply across the project, while the plan and tasks make the work concrete.

The benefit isn't simply having more documentation. It's having an agreed-upon description of the work that can be checked as the implementation develops.

The pattern I see is that exploratory work benefits from flexibility, while shared work benefits from a durable plan. The size of the change matters less than whether the decisions need to be preserved and communicated.

These recommendations are my judgment, based on using Pocock's skills and looking at what the different tools are designed to do. The refactoring case is the one I'd most like to test directly: does the additional planning in Spec Kit actually pay for itself when the goal is to preserve behaviour while changing the internal design?

Using both on the same project

There's no reason a project has to choose one approach forever. You might start with Spec Kit and use individual skills for day-to-day development, or begin with a lightweight workflow and introduce formal specifications when the work becomes more complicated.

The thing I'd avoid is maintaining two competing versions of the plan.

Suppose the constitution says one thing and an ADR says another. Which should the agent follow? It might choose one, or behave differently depending on the context it sees. Either way, you've introduced uncertainty into the process that was supposed to remove it.

A discussion in Pocock's repository about OpenSpec arrives at a similar conclusion: let the specification tool own the plan, use skills to work through decisions, and feed the results back into the specification.

The speckit-support-skills project takes this idea further. It adapts several of Pocock's skills to work with a Spec Kit project, using the constitution and specs/ directory as the source of truth. Its code review checks changes against those documents, and its retrospective can propose amendments to the constitution.

You can follow the same principle without a dedicated integration. Point CLAUDE.md to the constitution so the skills know where the project rules live. Keep the feature plan in one place, whether that's specs/ or your issue tracker. When a discussion resolves an important question, update the authoritative document rather than leaving the answer buried in the conversation.

The skills can still do their jobs. Grilling can expose a missing requirement, a glossary can clarify terminology, and an ADR can capture an architectural trade-off. Those are useful contributions to the plan, not reasons to create another one.

One plan, however you get there

I'm less interested now in whether a tool calls itself a framework or a collection of skills. The more important questions are whether it gives you the right amount of structure for the work and whether you can tell which decisions the agent is expected to follow.

Spec Kit and Pocock's skills offer different starting points. One makes a defined process the default; the other lets you assemble the process yourself. As both projects evolve, the practical difference is becoming more about how you work than what either tool can do.

I'd use the flexibility of skills when I'm still figuring things out, and lean toward a formal specification when the work needs a shared, lasting plan. There will be exceptions, and some projects will benefit from both.

But whichever approach I use, I want the same thing at the end: one authoritative place for the decisions that matter. The process can be flexible. The plan shouldn't be ambiguous.
